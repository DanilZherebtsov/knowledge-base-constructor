# STATE.md — структура и правила обновления

`STATE.md` в корне — единственное место для текущих планов и прогресса. Wiki хранит знания (append-mostly, с источниками, атомарно); STATE хранит намерения (частые перезаписи, без источников, всё в одном файле для обзорности).

## Структура

Фиксированный набор разделов, всегда в одном порядке. Пустые — с пометкой `_пусто_`, не удаляются (глаз привыкает к расположению).

Класс может переименовать/переосмыслить (пример: business — Профиль / Открытые направления / На этой неделе / Следующее / Календарь обязательств / Блокеры,риски,решения / Недавно завершено).>>

**Гранулярность отражает горизонт.** В начале — крупными мазками; по мере приближения дробится. Не атомизировать преждевременно (ложная точность).

## Правила обновления

1. **Источник правды.** STATE — единственное место для текущего плана. Никаких параллельных списков.
2. **Claude обновляет в трёх моментах:** (а) молча читает в начале сессии; (б) после завершения пункта переносит его в буфер «завершено»; (в) после ingest, меняющего приоритеты, — предлагает правку, человек подтверждает.
3. **Человек обновляет в двух:** смена приоритетов; новый блокер. Через чат или руками.
4. **Свежесть по дате.** Поле `_Обновлено:_` обязательно. Стартовый триггер свежести (что делать, если устарело) — в CLAUDE.md (always-on); здесь не дублируется.
5. **Связь с wiki — markdown-ссылками.** Пункт, ссылающийся на знание, делает это через `[Название](wiki/type/slug.md)`. Знание живёт в wiki; в STATE — формулировка и ссылка.
6. **Буфер «завершено».** Висит неделю, потом схлопывается: породившее wiki-страницу → ссылка на неё; под git рутина без следа → строка «N задач за период …, см. git log»; без git — удаляется. Память о работе — в wiki/git, не в STATE.
7. **STATE не canonical.** При конфликте с wiki/кодом — правда там. Lint может пометить расхождение, не правит автоматически.

## Передача в новый чат

Человек просит продолжить работу или взять новую задачу в другом чате («передай в новый чат», «дай хэндофф», «выгрузи контекст для нового чата») — запиши нужное так, чтобы чат без этой переписки смог работать. Резюме, которое будет читать человек, — не передача, а результат: в `output/`.

**Куда.** Человек назвал место, просит текст прямо в ответ или сказал, что продолжит не в этой папке (другая машина, облачная сессия), — так и сделай; в последнем случае дай текст передачи в ответе: файл туда не попадёт. Файл задачи, если он есть, всё равно допиши. Иначе, не спрашивая:

- **Задача уже ведётся своим файлом** (активная спека, рабочий файл вопроса, файл сравнения) — допиши в него раздел «Передача <дата>»: где остановились, что пробовали и отвергли, следующий шаг, что решено по ходу. Отдельный файл не нужен: решения по задаче живут при ней, а не во временном файле.
- **Новая задача, под которую в проекте заводят спеку** (фича, исправление; `specs/` в дереве «Архитектура» `CLAUDE.md`) — заведи спеку с тем, что уже известно: задача словами человека, что решено, что не входит — по правилам спеки (`status: active`, строка в `STATE.md`), и пометь в ней: постановка не написана и не проверена. Постановку и её проверку делает чат, который продолжит. «Разобраться», «проверить», «досмотреть», «выгрузить контекст» — не спека; сомневаешься — следующий пункт.
- **Остальное** — `tmp/handoff-<тема>-<дата>.md`. Приставка `handoff-` — всегда так, латиницей: по ней передачу узнают. Имя занято — добавь номер. Под git — до записи убедись, что `tmp/` есть в `.gitignore`; нет — впиши.

В первых двух случаях то, что узнали и что понадобится после задачи, предложи записать в вику сразу, в этом чате (`CLAUDE.md`, «Просьба решена»): отдельного файла передачи, который бы это донёс, нет.

**Что внутри файла или текста передачи:**

1. Первой строкой — задача словами человека.
2. Продолжение работы — где остановились, что пробовали и отвергли и почему, следующий шаг. Новая задача — что сделать, что уже решено, по чему принять. План из `STATE.md` и единицы работы не пересказывай — ссылайся на них.
3. Файлы — ссылками от корня проекта, не копиями. Этот чат сам начат с передачи — её отвергнутое и её раздел «Не записано в память проекта» перенеси в новую, а не ссылайся: та передача временная.
4. Раздел «Не записано в память проекта» — решения человека (его словами, с датой) и факты, которых нет в `wiki/` и которые понадобятся после задачи. Что записали в вику сразу — сюда не клади. Пусто — так и напиши. Передача временная: её содержимое не считается «уже записанным в файлах проекта».
5. Последней строкой: «Когда закончишь задачу — предложи человеку записать в память проекта (`wiki/`) то из раздела „Не записано в память проекта“, чего там ещё нет, и отметь здесь, что он ответил. Этот файл не удаляй: его назовёт профилактика.» В тексте для ответа и в разделе файла задачи — без второй фразы.

Значений секретов в передаче нет — только имя и где лежит ([secrets-rules.md](secrets-rules.md)).

**Человеку в ответе** — путь от корня проекта и фраза для нового чата с настоящим именем файла (задачи или передачи): «прочитай `<путь к файлу>` и продолжай».

**Зачем пункт 5.** Чат, начатый с передачи, этот раздел не открывает (а в Claude Desktop может не видеть и `CLAUDE.md`): его ведёт сам файл. Удаление он не предлагает, потому что в Claude Desktop удаление требует разрешения, которое открывает всю подключённую папку до конца чата, — ради одного файла его не просят; залежавшиеся передачи профилактика называет разом ([lint.md](lint.md)), удаление — только с «да» человека.
