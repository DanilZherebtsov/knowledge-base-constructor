# Миграция 0006 — переход проекта 1.x на 2.0.0

> **Исполняется агентом ВНУТРИ проекта 1.x**, на профилактике, по записи моста (`## base@51` и записи механик того же текста), или по шагу 0 «Проверки обновлений» нового `lint.md`, если переход прерван. Это **единственный путь** с 1.x на 2.0.0: промежуточные записи журнала и миграции 0001–0005 не применяются, номера частей в отпечатке не поднимаются. Этот файл читать с вершины ветки `main` зеркала (там последние исправления); файлы 2.0.0 брать **по тегу `v2.0.0`**; источник файлов 1.x — история того же зеркала. Знание — ADR-0063.

## Что меняется и главный инвариант

Конструктор 2.0.0 — один готовый проект одной версии: строка 3 `CLAUDE.md` — `> **Версия:** 2.0.0` вместо отпечатка сборки; решения, спеки, работа со своим кодом, оформление и роли есть в каждом проекте и читаются по виду задачи. Переход **на месте**: файлы конструктора заменяются версиями 2.0.0, а всё, что в них сказано о самом проекте, переносится в новые файлы.

**До «да» человека в проект не пишется ничего** (шаги 1–4), кроме двух действий шага 1: коммита автоисправлений этого же прогона (1.4) и `disableAllHooks` с согласия человека (1.5); разбор и черновики — во временной папке вне проекта.

> **Инвариант.** После «да» 0006 пишет только:
> - пути дерева `v2.0.0` (закрытый список, шаг 2);
> - `BACKLOG.md` — если раскладка `STATE.md` его требует;
> - строки перехода в `wiki/log.md` (литералы ниже);
> - файл хода;
> - коммит того, что незакоммиченным оставил этот же прогон профилактики (шаг 1.4).
>
> Всё остальное — байт-в-байт: тела `wiki/`, `wiki/index.md`, `raw/`, `input/`, `output/`, `specs/`, код, `tmp/`, `archive/` (под git), свои хуки и ключи `.claude/`, свои файлы с именами служебных файлов зеркала (`README.md`, `migrations/`, `CHANGELOG.md`). Временное (клон зеркала, разбор) — **только вне проекта**: прочитанный внутри проекта чужой `CLAUDE.md` среда применит как инструкцию.

**Литералы журнала** — строки `## [YYYY-MM-DD] обновление | …` в `wiki/log.md`, сверка по точному тексту после `| `:
- `переход на 2.0.0 — начат, начало <SHA>` (без git — `начало без git`) — пишется после «да»;
- `переход на 2.0.0 — сделан`;
- `переход на 2.0.0 — откат (<почему>)` — технический откат, не отказ человека: паузы нет;
- `переход на 2.0.0 — отказ`;
- `переход на 2.0.0 — отказ навсегда`;
- `не могу`.

**Файл хода** — создаётся после «да»: под git — `<git-dir>/0006/hod.md`, где `<git-dir>` = `git rev-parse --path-format=absolute --git-dir` (в рабочей копии `.git` — файл, путь берётся командой); без git — `archive/0006/hod.md`. В нём: «да получено <дата>», SHA начала, закрытый список, «что твоё» с решениями человека, список путей, которых в начале не было, отметка после каждого записанного файла.

**Переход завершён**, только когда строка 3 = `2.0.0`, в журнале есть `переход на 2.0.0 — сделан` и (под git) переход закоммичен.

**Перед любым вопросом человеку на шагах 1–2** — одна фраза сути: «конструктор вышел в новом виде, я могу перевести на него этот проект; сначала одно уточнение: …».

## Шаг 1. Вход (по порядку, без записи)

1. **Журнал и ход.**
   - Есть `— сделан` и строка 3 = `2.0.0`: под git переход не закоммичен — выполнить шаги 8.3–8.4, иначе шаг 8.4; стоп, переход сделан.
   - Есть `— сделан`, строка 3 — отпечаток 1.x, и файл хода отмечает пункт 8.1 — обрыв на шаге 8: выполнить шаг 8 с пункта 2. Файла хода с такой отметкой нет — правила вернулись к старым (например, слиянием ветки): сказать человеку «правила проекта вернулись к прежним — похоже, при слиянии; переводить заново?» и ждать.
   - Есть `— начат` без последующих `— сделан` / `— откат…` / `— отказ…` и файл хода с «да получено» — спросить «переход прервался <дата>, продолжаю?» и по ответу **продолжить**; под git — если начало (SHA из строки `— начат`) — предок `HEAD` (`git merge-base --is-ancestor <начало> HEAD`) и коммиты после него трогали только пути закрытого списка, `BACKLOG.md` и `wiki/log.md` (иначе — показать человеку, какие ещё пути менялись, и спросить). Продолжение — с первого неотмеченного файла шага 6, клон и разбор — заново (шаги 2–3); старые версии — из `git show <начало>:<путь>` (без git — из резервной копии шага 5). Неотмеченный файл отличается от старой версии — после обрыва в проекте шла работа: старой считать текущую и сказать человеку. В файле хода нет размера главного файла (шаг 5.5) — сначала повторить шаг 5. Файла хода нет или в нём нет «да получено» — начать с шага 2.
   - Иначе — начать с шага 2.
2. **Git, шелл, зеркало.**
   - Нет git (`git rev-parse` падает) — путь «без git» (шаги 5 и 7).
   - Нет шелла или нет доступа к зеркалу (проект Claude Desktop, не вкладка Code; песочница без сети) — фраза сути и просьба: «открой проект во вкладке Code или в Claude Code — там переход пройдёт». Строку `не могу` писать, только если человек ответил, что не может или не будет; переход в таком окружении не предлагать 4 недели, в окружении с шеллом — предлагать как обычно.
3. **Репозиторий** (`git rev-parse --path-format=absolute --show-toplevel --git-dir --git-common-dir`):
   - `--show-toplevel` ≠ папка проекта — проект лежит внутри большего репозитория: сказать и спросить, как быть;
   - **общий репозиторий** — авторов-людей в `git log --format=%an` больше одного (боты, `noreply` и один человек под разными адресами — не в счёт; неглубокий клон считать общим; сомнение — спросить): переход — в отдельной ветке под MR от той ветки, куда в проекте вливают изменения правил (правило проекта называет её — взять оттуда; не называет — спросить). Текущая ветка не она — назвать и ждать: разбор идёт только по ней. Переход разрешён и в рабочей копии git (`--git-dir` ≠ `--git-common-dir`), если она на этой ветке; ветку в чужой папке не переключать;
   - **один автор** — рабочая копия (`--git-dir` ≠ `--git-common-dir`): не переходить, назвать основную папку. Основная ветка — `origin/HEAD`; его нет, а локальная ветка одна и отслеживает `origin/<та же>` или `origin` нет вовсе — она и есть основная; иначе, если текущая не основная, — спросить;
   - есть `origin` — `git fetch`. На ветке, куда вливают правила (один автор — на основной), строка 3 в `origin` уже `2.0.0` — переход сделан: сказать «влей <ветку> в свою», стоп. Текущая ветка отстаёт от неё — сказать и ждать.
4. **Незакоммиченное.**
   - Идёт слияние, rebase или cherry-pick — сказать и ждать.
   - Сделанное **этим же** прогоном профилактики (автоисправления) — закоммитить по правилу проекта, иначе сообщением `lint: автоисправления перед переходом`.
   - Незакоммиченные правки человека или команды в путях закрытого списка, `STATE.md`, `BACKLOG.md`, `wiki/log.md` — не коммитить самому: сказать и ждать. В прочих путях — не препятствие.
   - Неотслеживаемые и игнорируемые файлы — не препятствие; если путь из закрытого списка — его копия пойдёт в резервную (шаг 5).
5. **Чужие хуки и правила «коммить после ответа».**
   - Хуки в `.claude/settings.json`, `.claude/settings.local.json` и `~/.claude/settings.json`, которых нет в 2.0.0 (свои у 2.0.0 — `freshness_check.py`, `consent_nudge.py`, `judge.py`), коммитящие или пушащие — предложить на время перехода `"disableAllHooks": true` в `.claude/settings.local.json` и **продолжить в новом чате** (хуки берутся при старте сессии). Не согласен — переход не начинать. Стражи, которые ничего не пишут (проверки перед командой), — не трогать.
   - Правило проекта «коммитить или пушить после каждого ответа / работы» до шага 8 не применять — сказать человеку одной строкой.

## Шаг 2. Снимок (вне проекта)

1. **Клон зеркала** — по тому же адресу, что в шаге 2 «Проверки обновлений» твоего `methodology/lint.md`; вне проекта, полный (без `--depth`: нужна история 1.x):
   ```bash
   D=$(mktemp -d) && git clone -q <адрес зеркала> "$D" && git -C "$D" checkout -q v2.0.0
   ```
   Тега `v2.0.0` нет — человеку: «новый выпуск конструктора ещё не выложен до конца, вернусь к этому на следующей профилактике»; строку `не могу` не писать, стоп.
2. **Закрытый список** — файлы дерева `v2.0.0`, которые попадают в скачанный архив:
   ```bash
   git -C "$D" -c core.quotePath=false ls-tree -r --name-only v2.0.0 \
     | while IFS= read -r p; do git -C "$D" check-attr export-ignore -- "$p" | grep -q ': set$' || printf '%s\n' "$p"; done
   ```
3. **Источник 1.x — по частям** (строка 3 твоего `CLAUDE.md`: `base@N · <механика>@M · … · <класс>@K`):
   - файлы `base/` (в том числе `ASSEMBLY.md` и корень зеркала того времени) — **последний** (самый новый) коммит зеркала, где в `versions.json` `base` = N;
   - файлы механики (`mechanics/<имя>/`, её `_about.md`) — последний коммит, где номер этой механики = M; файл класса (`presets/<класс>.md`) — где номер класса = K;
   - номер не встречается ни в одном коммите — ближайший меньший, человеку строкой на экране; номер ≥ значения моста (51 у `base`) — источник — тег `v1-final`.
   ```bash
   # от новых к старым; первый подходящий — последний коммит с этим номером
   for c in $(git -C "$D" log --format=%H v1-final); do echo "$c"; git -C "$D" show "$c:versions.json" 2>/dev/null; done
   ```

## Шаг 3. Что твоё (разбор вне проекта)

Агент сам, **по смыслу**, по каждому файлу закрытого списка, который есть в проекте (заготовки под `wiki/`, `raw/`, `input/`, `output/` не разбирать: шаг 6 их не пишет). Сверка — с **любой** версией 1.x той же части в истории зеркала (проект мог обновляться по записям журнала и сохранить старые или более новые формулировки) и с текстом `v2.0.0`. Опора для заполнений сборки — `ASSEMBLY.md` (с коммита источника `base`) и `_about.md` механик (с их коммитов): там описано, что сборка вписывала в слоты.

Каждое место, где файл проекта отличается, — в одну из трёх групп:
- **(а) Конструктора** — текст любой версии 1.x этой части, текст `v2.0.0` или заполнение слота общими словами по описанию сборки (дежурные формулировки класса, перечни механик). Не переносится.
- **(б) О самом проекте** — переносится в соответствующее место файла 2.0.0:
  - раздел «О проекте» — дословно, вместо врезки первого контакта 2.0.0;
  - строки дерева «Архитектуры» о своих подпапках `raw/`, своих типах вики, местах `output/`, своих ролях и папках;
  - заполнения слотов фактами о проекте: валюта, единицы, свои типы вики и каскады в них;
  - формат и проверки своего типа вики (в `methodology/page-conventions.md`, `lint.md`), перечень `type` — слиянием с перечнем 2.0.0, в его форме;
  - свои правила человека, в том числе **заменившие** правило конструктора — заменой того же правила в 2.0.0, не дописыванием рядом;
  - разделы, помеченные как расширение, — целиком.
- **(в) Неясно — в экран «спрашиваю».** Сюда же — правило конструктора, которое человек у себя **удалил**: в 2.0.0 оно есть, удалять ли снова — решает он.

**Отдельные файлы:**
- **`HELP.md`** — переносится только сказанное о самом проекте; перечни возможностей — из 2.0.0.
- **Образцы ролей, хуки, `.claude/output-styles/plain.md`:** файл равен этому файлу в **любом** коммите зеркала с тем же номером части — заменить на 2.0.0; иначе — по смыслу, как выше. Свои роли (не образцы) не трогать; образцы 2.0.0, которых нет, — добавить.
- **`.claude/settings.json`** — слиянием по записям:
  - свои ключи и записи (хуки, `permissions`, `env`) — байт-в-байт;
  - запись с командой хука 2.0.0 в прежнем виде (старый `matcher`) — заменить записью 2.0.0, не добавлять вторую;
  - запись хука или `outputStyle` 2.0.0, которой в проекте не было, — **в экран «спрашиваю»** (кроме явного решения против — тогда не ставить): строки журнала `настройка | хуки: не ставим`, `настройка | стиль: не ставим`, файл `.claude/knowledge-check.off`, запись, которую человек сам удалил (видно в `git log -p -- .claude/settings.json`);
  - то, что уже стоит в `.claude/settings.local.json`, — не дублировать;
  - общий репозиторий — `outputStyle` только по вопросу, как в миграции 0005.
- **`STATE.md`** — раскладка по семи разделам 2.0.0 (Стадия · Путь до цели · Сейчас в работе · Следующее (1–2 недели) · Календарь обязательств · Блокеры, риски и решения, ждущие меня · Недавно завершено) по таблице: все названия разделов из `state-rules.md` источника 1.x (`base` и механик) → раздел 2.0.0. Основные соответствия:
  - «Профиль момента» → «Стадия»;
  - «Открытые направления» → «Путь до цели»;
  - «На этой неделе» → «Сейчас в работе»;
  - «Завершено за последнюю неделю», «Отвечено за последнюю неделю» → «Недавно завершено»;
  - «Блокеры и риски» → «Блокеры, риски и решения, ждущие меня»;
  - «Известный техдолг» → `BACKLOG.md` (файл есть — в его подходящий раздел, нет — создать);
  - раздела нет — `_пусто_`; `_Обновлено:_` — дата перехода, прежнее пояснение после даты — после закрывающего `_`.
  Ни одна строка содержимого не теряется.

Итог разбора — во временной папке вне проекта (`$D-razbor.md`).

## Шаг 4. Один экран, одно «да»

Человеку — **одно** сообщение, простыми словами, без слов «версия, тег, слияние, миграция, отпечаток, механика, база» (и прочих запретных слов твоего `lint.md`). Три группы:
1. **Что меняется** — 2–3 фразы сути (проект переходит на готовый набор правил; работа с кодом, решения, спеки и оформление есть сразу и включаются по задаче; справка и память прежние; записи не трогаются) и **обязательно, по действию:**
   - отложенные планы будут жить в отдельном файле (`BACKLOG.md`), который я не читаю в начале чата — открываю его, когда закрыт этап или «Следующее» пусто;
   - файлы в `output/`, которые месяц не менялись, профилактика будет переносить в архив (в первый раз — со списком);
   - следующая профилактика приберёт план по новым правилам.
2. **Что у тебя своё и куда переношу** — коротко, по группе (б).
3. **Что спрашиваю** — пункты (в); перенести ли свои правки в `HELP.md`; разложить ли план (`STATE.md`) по новым разделам; включить ли то, чего в проекте не было: новый вид ответов (сверху — что решить сейчас, ниже — остальное) и проверку ответов отдельной быстрой моделью (ответ иногда приходит на секунды позже).

И вопрос: «переходим? Можно ответить и „больше не предлагай“». Ответы на пункты — тем же сообщением.
- **«Да»** — шаг 5.
- **Частичное «нет»** на `HELP.md`, `STATE.md`, вид ответов или проверку — этот файл или запись остаются как были, строкой в журнале после перехода (`настройка | при переходе: HELP.md оставлен` / `STATE.md оставлен`; `настройка | стиль: не ставим`; `настройка | хуки: не ставим`).
- **«Нет»** — строка `переход на 2.0.0 — отказ`, стоп (в проекте больше ничего не записано). **«Больше не предлагай»** — `переход на 2.0.0 — отказ навсегда`. В обоих случаях удалить временное вне проекта; хуки выключали на шаге 1.5 — напомнить убрать `disableAllHooks`. Общий репозиторий: строку отказа писать, только если отвечающий решает за правила проекта (спросить); иначе не писать, предложение повторится.

## Шаг 5. Начало (после «да»)

0. **Общий репозиторий** (шаг 1.3) — создать ветку под MR от `HEAD` сейчас, до записи; начало = её вершина.
1. Строка журнала `переход на 2.0.0 — начат, начало <SHA HEAD>` (без git — `начало без git`).
2. Файл хода: «да получено <дата>», SHA начала, закрытый список, «что твоё» с решениями человека по экрану, пути закрытого списка и `BACKLOG.md`, **которых в начале нет** (`git cat-file -e <начало>:<путь>` падает).
3. **Под git — статус «до»** в файл хода:
   ```bash
   git -c core.quotePath=false status --porcelain -uall --ignored=matching
   ```
   Неотслеживаемые и игнорируемые пути закрытого списка, которые есть на диске, — копией в `<git-dir>/0006/before/`.
